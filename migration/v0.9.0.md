# Migrating to v0.9.0

If you're upgrading from v0.7.x, read [v0.8.0.md](./v0.8.0.md) first.

## TL;DR

| Change | Affected callers | Section |
|---|---|---|
| `Task.Wait` / `WaitFor` return `*TaskFailedError` when the task fails | every caller that waits on a task | [Failed tasks are errors](#task-waits-report-failed-tasks-as-errors) |
| `WaitForCompleteStatus` also returns `*TaskFailedError` alongside `status == false` | callers that treat any `err != nil` as a transport error | [WaitForCompleteStatus](#waitforcompletestatus) |
| `"WARNINGS: n"` exit status is now a success (`IsSuccessful`, not `IsFailed`) | callers that read `IsFailed` / `IsSuccessful` after `Ping` | [Warnings](#warnings-are-a-success) |
| Waits return `ctx.Err()` as soon as the context is done | callers that relied on a wait finishing its current sleep first | [Context cancellation](#context-cancellation) |
| `Ping` no longer touches the `Is*` flags when the status request fails | callers that read the flags after a failed `Ping` | [Ping](#ping) |

The first row changes behaviour without changing any signature, so the
compiler won't flag it. Read that section even if your code builds.

---

## Task waits report failed tasks as errors

Before v0.9.0, `Task.Wait` and `Task.WaitFor` returned `nil` once the task
stopped running, whatever its exit status. A task that PVE reported as
failed, for example `VM quit/powerdown failed - got timeout` or
`VM 100 already running`, looked like a success unless the caller also
checked `task.IsFailed`. Callers that forgot treated a failed shutdown as done
and started the next operation against a VM in an unexpected state.

The waits now return a `*TaskFailedError` when the task finishes with any exit
status other than `OK` or `WARNINGS: n`:

```go
type TaskFailedError struct {
    UPID       UPID
    Node       string
    Type       string // e.g. "qmshutdown"
    ID         string // e.g. "100"
    User       string
    ExitStatus string // PVE's message, verbatim
}
```

`Error()` reads like
`task UPID:pve1:...: (qmshutdown 100 on pve1) failed: VM quit/powerdown failed - got timeout`.

```go
// before: the error only covered transport problems and timeouts, so the
// exit status had to be checked separately
if err := task.Wait(ctx, time.Second, 5*time.Minute); err != nil {
    return err
}
if task.IsFailed {
    return fmt.Errorf("shutdown failed: %s", task.ExitStatus)
}

// after: a failed task is an error
if err := task.Wait(ctx, time.Second, 5*time.Minute); err != nil {
    return err // *TaskFailedError, ErrTimeout, ctx.Err(), or an API error
}
```

The old `IsFailed` check still works. It is redundant now, but harmless.

To branch on the failure itself, use `errors.As` or `IsTaskFailed`:

```go
err := task.WaitFor(ctx, 120)

var tfe *proxmox.TaskFailedError
switch {
case errors.As(err, &tfe):
    log.Printf("%s %s on %s failed: %s", tfe.Type, tfe.ID, tfe.Node, tfe.ExitStatus)
case proxmox.IsTimeout(err):
    // still running after 120s
case err != nil:
    // couldn't read the task status, or ctx is done
}
```

### Code that deliberately ignored failures

If you start a task that is expected to fail sometimes and you only want to
know that it finished, filter the new error out:

```go
if err := task.WaitFor(ctx, 60); err != nil && !proxmox.IsTaskFailed(err) {
    return err
}
```

### Tasks PVE has forgotten

The status endpoint answers `no such task` once a task's status file has
gone, which can happen for old or rotated tasks. The waits used to return that
error. They now check the node's task index (`GET /nodes/{node}/tasks`) for the
task's final status and only return the original error if it isn't listed
there either. A failure found in the history is reported as a
`*TaskFailedError` like any other.

## WaitForCompleteStatus

`WaitForCompleteStatus` keeps its `(status, completed bool, err error)`
signature. For a failed task, `status` is still `false` and `completed` is
still `true`, but `err` is now a `*TaskFailedError` instead of `nil`:

```go
// before
status, completed, err := task.WaitForCompleteStatus(ctx, 30)
if err != nil {
    return err // only transport errors
}
if completed && !status {
    return errors.New("task failed")
}

// after — the same code still works, but the failure now arrives through err
// first. To keep both branches distinct, check for TaskFailedError:
status, completed, err := task.WaitForCompleteStatus(ctx, 30)
if err != nil && !proxmox.IsTaskFailed(err) {
    return err
}
```

## Warnings are a success

PVE reports `WARNINGS: n` as the exit status of a task that finished but
logged warnings, and counts it as a success. `Ping` used to set `IsFailed` for
it, because it only treated `OK` as success. It now sets `IsSuccessful`, the
waits return `nil`, and the count is available in the new `Task.Warnings`
field:

```go
if err := task.WaitFor(ctx, 300); err != nil {
    return err
}
if task.Warnings > 0 {
    log.Printf("%s finished with %d warning(s); see task.Log", task.UPID, task.Warnings)
}
```

`ExitStatus` still holds the raw `WARNINGS: n` string.

## Context cancellation

The waits used `time.Sleep` between polls, so a cancelled context was only
noticed at the next poll. `Wait`, `WaitFor`, `WaitForCompleteStatus` and the
`Watch` tail loop now wait on `ctx.Done()` and return `ctx.Err()`
(`context.Canceled` or `context.DeadlineExceeded`) immediately:

```go
ctx, cancel := context.WithTimeout(ctx, 2*time.Minute)
defer cancel()
err := task.Wait(ctx, 5*time.Second, 10*time.Minute)
if errors.Is(err, context.DeadlineExceeded) {
    // the context deadline (2m) fired before Wait's own max (10m)
}
```

`ErrTimeout` is still returned when `Wait`'s own `max` is reached first.

`Wait` also no longer pings the task twice before its first sleep. A
non-positive `interval` now falls back to `DefaultWaitInterval` instead of
panicking.

## Ping

`Ping` used to recompute `IsRunning` and the other flags even when the status
request failed, which left `IsRunning == true` on a task it had just failed to
read. On error it now returns the error and leaves the task as it was after
the last successful `Ping`. It also keeps the task's `UPID`, `Node`, `Type`,
`ID` and `User` if the status response leaves them out.

`Ping` still doesn't treat a failed task as an error. It only refreshes
state. Use `Wait` if you want the failure as an error.

## Nothing else

There are no other source-incompatible changes in task handling. New
exported identifiers: `TaskFailedError`, `IsTaskFailed`, `Task.Warnings`,
`TaskStopped`, and `TaskExitOK`.
